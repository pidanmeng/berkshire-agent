# 找简化

把宽泛的「找东西简化」请求转成有证据、可落地的简化提案。这是指引，不是清单：跟着代码走，保持判断力，用少量被充分证明的候选好过一大堆薄猜测。

## 先读仓库上下文

- 读根 [AGENTS.md](../../../AGENTS.md) 与 [docs/secondary-development.md](../../../docs/secondary-development.md)：**目标态 vs 已实现**诚实纪律是本仓库最重要的判断锚——不要对 `packages/`、`ctx.*`、`@berkshire/cordis` 等「未实现但位列 docs 的设计」做"删了它"的简化，除非那是显式的设计放弃。
- 动任何 `docs/` 里的目标态文档前，先判断是「文档表达冗余/语气问题」（可简化文案）还是「设计面被删」（需谨慎、属设计决策）。前者归 [bk-doc](../bk-doc/SKILL.md)/[bk-prose-standard](../bk-prose-standard/SKILL.md)；后者几乎总是需要讨论而非直接砍。

## 什么算强候选

真正的简化移除/折叠/降级某样真实存在的东西，并有明确证据表明当前设计代价大于收益：

- 一个公共方法、事件、配置旋钮、注册通知、辅助函数、包、持久事件或测试产物**没有生产消费者**（即不在 `src/` / 真实入口被引用）。
- 测试或文档是唯一消费者，且其钉住的行为不承重。
- 两处表示镜像同一事实（尤其持久化事件 vs 临时的 `agent/*`/`sync/*` 事件成对出现）。
- 某个 seam 有每个实现都必须支持、却无消费者使用的方法。
- 某包仅因测试/演示/支持代码而存在。
- 某功能实现的是投机性通用性（无产品 owner 的过度设计）。
- **手写代码重复实现了「仓库技术栈内已存在」的东西**：as RSPC/specta、DuckDB 能力、Cordis timer、ECharts——若该已存在物经过验证不需手写，用依赖/平台能力替换并删除实现+专用测试。
- 简化后的行为可能略有不同，但新行为仍合理且更易解释。

薄候选不足以写成提案：删一行、跑一次静态扫描、把「这看起来复杂」而没有调用点证据——都不够。

## 广撒网

当用户要求广度或多候选时，用并行 subagent 分域调查，每域要求证据而非猜测。BK 有用分域：

- 前端骨架（`apps/berkshire-agent/src`）：React zustand 现状、死组件、冗余路由。
- Rust 骨架（`src-tauri`）：`lib.rs`/`main.rs`、Cargo 依赖、tauri.conf.json。
- 文档语料（`docs/`）：冗余、目标态被当已实现的声张、可折叠的实现细节。
- 生成图（`docs/diagrams/*.candidate.json`）：是否与对应 `.html` 及架构文档一致。

若无 subagent 可用，自己模拟广度。别让第一个好候选挡住调查。

## 证成或否决每个候选

给每个符号/行为先分类其消费者再写：生产（`src/`、真实入口、Cargo/bin、真实配置）vs 非生产（测试、README/docs、生成的 expected、注释）vs 模糊（示例/脚本，需检视归因）。

用 `rg` 先搜精确符号、事件名、包名、配置键、方法名（同时 `.name(` 与 `name(`）、以及任何 wire 字符串。然后读调用点、公共接口、动态事件名、测试、文档。

否决/降级：

- 存在生产调用方，则简化是产品决策而非清理；
- 被明确的已实现理由或硬防御模式正当化，新证据不足以推翻；
- 删除会带来无关重构却没有真正减少公共 API 或必需行为；
- 想法正确但太小——加 `TODO`/`FIXME` 即可，不写提案。

## 简化文案

把注释与文档当受维护面，应用 [bk-prose-standard](../bk-prose-standard/SKILL.md)。删重述代码/在他处已解释的注释；文档保留在它所属层级，省略实现细节与罕见用例（除非改变维护契约）。

## 读信任与生命周期边界

对每个防御拷贝/freeze/校验/回调捕获，说明值来自哪、下一步由谁拥有。同进程的类型化调用通常借用只读；解析器/配置加载器/队列/模型-工具 JSON/耐久文件/worker/进程/wire 解码器拥有或校验其数据。围绕「敌意 getter、假类型对象、回调替换、同进程交接后变更」构建的测试，是潜在投机契约的证据，不是保留它的自动理由。

## 写提案（落地输出）

BK 目前**没有 `.agents/notes/` 决策记录系统**。因此简化提案按以下形态落地：

1. **小、局部清理**：加 `TODO`/`FIXME`/`XXX` 内联注释，按紧急度命名（`TODO(name):`），一句说清为何安全可折返、什么动作能简化它。
2. **中等、需讨论的设计面**：在对应 PR 描述/讨论提「简化提案」段（现状 + 害处 + 简化方案 + 证据 + 放弃什么），不直接删目标态设计。
3. **纯代码死物清理**：直接删并补相关测试/文档更新，PR 说明删了什么证据。

## 校验与 PR 卫生

- 纯文档/文案类：跑 `git diff --check`，核对链接与术语（[bk-doc](../bk-doc/SKILL.md)）。
- 前端骨架代码：`cd apps/berkshire-agent && bun run build`；Rust：`cargo check`。
- 输出 PR 总结：删/新增/合并了多少候选、调查的主域、刻意排除的项、跑过的检查；每项命名旧/新，说明完整替换证据与为何删安全。
