# Berkshire Agent 文档标准

使每篇文档**可搜索、新手可读、对 AI 与维护者足够精确**。先应用本仓库的 [AGENTS.md](../../../AGENTS.md) 与「诚实标注」纪律，再用本技能的流程整理结构与事实。保持「一个事实一个家」：源码、测试、生成目录、package README、指南、决策记录各有其唯一的事实从属。

本技能承接 dsh 的文档标准思路，但**项目主语言为中文、无独立文档网站/无双语配对设施**——因此不引入 dsh 的 kind 元数据系统、文档网站投影、翻译配对机制（若未来引入中英对照，见 `bk-translate-docs`）。

## 工作流

对每个请求范围按序执行：

1. **诚实分级**：先读 [secondary-development.md §6](../../../docs/secondary-development.md#6-已有-vs-目标诚实标注) 与 [architecture.md §11](../../../docs/architecture.md#11-关键文件索引现状--目标)。明确所写内容是「已实现（`apps/berkshire-agent` 骨架）」还是「目标态（`packages/`、`ctx.*`、`@berkshire/cordis`、DuckDB 写者等）」。
2. **定位归属**：package/模块契约放代码旁；跨包学习、用户、开发者、架构、讨论材料放 `docs/`；AI 工作流放 `.agents/`。不新建层级去重复已有事实。
3. **明确读者**：写之前定义读者的起始状态、可观察输出、可能的失败与恢复路径。
4. **按序撰写**：`标题` → 一句话定位 → `Summary`（做了什么）→ 分层（用户/开发者）→ 交叉引用。目标态文档必须在开头用醒目标注声明「目标态」。
5. **逐条核对诚实**：把「已实现 vs 目标态」写在文档可见处，命令类声明标注其真实可用性（对照 [AGENTS.md 命令节](../../../AGENTS.md#命令bun-版)）。
6. **跑校验**：本篇落地的文本改完，核对链接锚点、术语统一、示例自洽；存在可运行骨架改动时补 `bun run build` + `git diff --check`。

## 事实核对：运行它，而非假设它

文档对某项操作/命令/默认值/错误/平台差异的声明，**唯一可接受的证据是运行过它**。这是每篇新文档、每段声称操作的新段落的强制步骤：

1. **运行每条声称的操作**：把 CLI 命令、配置片段、示例对着当前 checkout 执行，只记录观察到的输出、警告与失败模式（真实现有命令见 [AGENTS.md 命令节](../../../AGENTS.md#命令bun-版)）。
2. **删除你复现不了的**：不凭记忆、类比或邻包 README 搬运命令/字段/默认值。若目标态命令（如 `cargo test -p bk-core`、`bk --dump-config`、`provider check`）尚未存在，如实标「待实现」，绝不写成可运行。
3. **声明依赖密钥/网络的**：若声称依赖某个 key 或网络而你没有，注明并指定验证所有者，勿断言行为。
4. **禁止把示例当实现**：文档示例若依赖未存在的 `ctx.*`/模块，必须标「目标态示例」，不得让读者误以为可 import。

## 文风规则（Voice rules）

- **Summary 说它做什么**：开篇描述读者能用它做什么/何时选它/主要代价，不罗列其内部角色、注册或组件清单（「注册 ctx.dataSources」是身份叙述；「你可以把日K/实时/财务从一个源切到另一个」才是它做什么）。（承接 [bk-prose-standard](../bk-prose-standard/SKILL.md) 的「完成命题」原则。）
- **开发者节解释而非罗列**：覆盖整体设计概念、架构、手绘数据流即可，细节链回代码；不堆 API 全目录、整列清单、JSDoc 复述。
- **只写当前状态**：普通文档描述当前代码库。目标态用「目标架构」显式声明；`docs/reference/` 的审计/研究记录保留其历史范围。禁止「推理过程泄漏」（见 [bk-trim-cot-leakage](../bk-trim-cot-leakage/SKILL.md)）。
- **中文为主**：本仓库文档以中文为主，术语保持统一（`能力缝 seam`、`三角色`、`dispatch (@mode)`、`profile/bundle/patch`、`单写者`、`fail-closed`）。

## 质量判据

- **简洁**：常见路径只含达成结果所需事实；完整真相留在链接或更深层。
- **直观**：前提先于依赖概念，下一步清晰，标题用读者会搜索的词。
- **准确**：每条持久声明有一个事实归属者，验证路径与其风险相称。
- **诚实**：明确区分「已实现」与「目标态」，命令可复现性如实标注。
- **新手可重建**：无仓库背景的工程师通过 3~5 个链接页可重建相关架构。

## 审计语料

读而非重述其所有者的契约：根 [AGENTS.md](../../../AGENTS.md)、[docs/architecture.md](../../../docs/architecture.md)（含 §11 锚点纪律）、[docs/secondary-development.md](../../../docs/secondary-development.md)（含 §6 诚实标注）。对范围内每篇面向用户文档应用撰写顺序。用 [bk-trim-cot-leakage](../bk-trim-cot-leakage/SKILL.md) 查推理泄漏，用 rg 找重复规则，删「复制出来的目录/状态清单」（保留其权威 owner 的链接），并从已实现文档里移除把目标态当已实现的声张（诚实见 [AGENTS.md](../../../AGENTS.md)）。每条关键的规则一至三行 + 链接到其出处。

## 校验（Validation）

- 落地的文本改动：核对链接（锚点存在、跨文件不悬空）、术语统一、示例与目标态文档自洽。
- 骨架/代码改动伴随 `bun run build`（`apps/berkshire-agent` 真实可跑）与 `git diff --check`。
- 无独立文档门禁脚本；任何命令类声明必须手工复现（见上）。
