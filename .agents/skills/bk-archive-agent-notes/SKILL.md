# 决策记录的维护（待实现）

> **⚠ 状态：待实现。** 本仓库目前**没有 `.agents/notes/` 决策记录系统**：无 active/archived 分类、无归档机制、无校验脚本。本文是「若未来建立决策记录体系」应遵循的生命周期流程与取舍说明——当前不可管理任何记录，**不要把它当可用能力**（诚实见 [AGENTS.md](../../../AGENTS.md)、[secondary-development.md](../../../docs/secondary-development.md)）。

## 取舍说明

- BK 的设计意图集中在 `docs/*.md` 的目标架构文档集 + `docs/reference/`（审计/研究）——**这是「已提交事实」的主要家**，不以「决策记录」形态存在。
- 若未来发现需要记录「某次权衡/备选/放弃的独有理由」（尤其简化提案、能力缝取舍、数据契约决道），才建立 `.agents/notes/<lifecycle>/<class>/yyyy-mm-dd-topic.md`。
- 在体系建立前，简化/设计的理由落在 PR 描述或 `docs/` 里横向可见处（见 [bk-explain-simplifications](../bk-explain-simplifications/SKILL.md)）。

## 若建立体系：生命周期流程（假设性）

**读契约**：先读决策记录规则（若能建立）与该分类的 active 生命周期说明，再分类。用当前代码、配置、包文档、更新文档、入链来确定某个理由是否仍拥有或约束任何东西。

### 新增时查超驰（supersession）

每个新决策记录触发对覆盖同一决策/机制/被拒备选的活动记录做一次限定审计。分类每项全/部分超驰：把符合归档条件的 `implemented` 记录在同一 PR 内归档；部分超驰或独立有用的理由保留并交叉链接；被拒的过时提议「删除」（若不再防止一类的常见错误）或保留（若仍是可识别的陷阱）。

### 按未来价值分类

- **已实现——保留 active**：其理由/备选/负向保证/耐久-语义/归属边界/安全规则/回引条件是未来变更可能受益的。长度无所谓。
- **已实现——归档**：已发货决策完整且正文不太可能指导未来（一次性 UI 镀层、窄适配器、已关闭的次要 bug、被新实现取代的细节）。
- **提议——永不归档**：保留活动提议；不值得继续就诚实拒绝。
- **被拒——仅保留为护栏**：仅当失败方案仍是可识别的意义错误且记录解释了为何失败。
- **被拒——删除**：失败想法已过时/被取代/不再可能/不再防止重开，删除整组并修入链。

不要为凑数归档。逐条语义判断，同类同原则。

### 归档一个三元组

若采用双语记录（每篇 `foo.md` + `foo.zh.md` + `foo.i18n.yaml`），归档把完整三元组从 `implemented/<class>/` 移到 `archived/<class>/`；正文零编辑，仅在 `Status: implemented` 下插入 `Archived: YYYY-MM-DD`（两侧同值）；重新记录 sidecar 哈希；搜索入链并重定向到当前权威或删除。归档后**永不编辑/移动/翻译/格式化/删除**（历史快照，不是当前行为权威）。

## 验证与报告

**当前无任何验收集可跑**（无记录 = 无门禁）。若体系落地，则跑对应校验（对应 dsh 的 `verify-archived-agent-notes`——BK 以 bun 形态实现）+ `git diff --check`；报告保留的 active、归档的 implemented、保留/删除的被拒、被迫的提议，及每个真正 borderline 案例与其字数与选择。
