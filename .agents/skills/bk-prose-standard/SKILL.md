# Berkshire Agent 文案标准

写足以保住契约，再删掉推理过程、重复与装饰。**契约**是调用方、被调方、实现方、生产者或消费者依赖的义务、不变量、前置条件、后置条件或兼容承诺。本技能拥有编辑判断与必需文案覆盖的裁决权；文档的摆放与结构见 [bk-doc](../bk-doc/SKILL.md)，推理泄漏的排查见 [bk-trim-cot-leakage](../bk-trim-cot-leakage/SKILL.md)。它是指引，不是脚本。

`contract/boundary/shape/surface/seam/gate/vocabulary` 等词先用后判，不是禁用词：先问「精确规则、API、字段集、类型、校验、时序点、组件切分或失败态」是否说得更准。在指精确技术对象（调用方/被调方契约、安全/进程边界）时保留该词。

注释描述代码表达不了的**非显然契约或理由**；不重述代码已暗示的内容。

## 输入与排除

- 要求明确 `scope`；缺失时报所需输入并停下，不猜测全仓库范围、不开始采访。
- `mode: automatic | interactive`，默认 automatic；仅当用户显式要求提问/校准才进 interactive。
- 一律排除 `vendor/`（若出现）与 `.agents/notes/archived/`（若未来建立 notes 体系；历史快照冻结，不现代化其措辞或出链）。
- 生成目录/快照/夹具是派生品：改其 owner 源再重新生成，不直接编辑派生品。

## 保留完整命题

编辑前识别段落中的每个命题，并保留每项相关的：行为者与动作；条件、时序与顺序；情态（必须/可能/绝不）；负向保证与例外；归属、副作用、失败模式与后果。只有每个事实分句都存活且结果更清晰时，才删形容词、重复与叙述。字数少本身不是改进。

在使用点保留完整的局部契约（行为、失败、归属、后果）；架构/理由/算法/历史/扩展示例则激进地链到拥有文档。一个解释一个家；必要契约事实可在本地重复。

## 按文案位置的必需覆盖

不是单向精简：当代码、类型、结构表达不了下列必需契约时，要补文案。

- **公共 JSDoc**：写清调用方可见的返回差异、抛错/拒绝、副作用、归属、时序、取消、耐久性。
- **内部注释**：定位非局部结构与显然复杂的局部结构——不变量、竞态顺序、归属、安全边界、意外失败行为；删控制流叙述与代码重述。
- **模块注释**：说明模块角色、依赖、职责与非显然架构选择；架构选择链到其拥有解释。
- **测试**：只解释非显然的测试设计——为何需要该夹具/断言/平台迁就/真实入口/间接观察；删走查与清单。
- **README/指南**：包含消费方契约（配置、语义、失败、限制、扩展点、模型可见效果）；链接生成目录与跨包 owner；保留持久缺口与维护者陷阱。
- **决策记录/Agent Notes**（若建立）：保留独特理由、机制、备选、后果、已发货验证证据与命名覆盖缺口；已实现记录用现在时陈述已发货现实，删规划清单（不删钉住决定的证据）。
- **技能与代理指令**：写行为护栏与显式范围限制（如「指引，不是脚本/清单」）；工作流保持简洁并链其真相来源。
- **提示词与可见字符串**：把措辞当行为。前端 UI 文案走类型化词典（计划中的 `ctx.clientModules`/slot 规范），检查文本、无障碍名、tooltip、占位符、格式模板一起审；模型可见文本更新其拥有的可运行快照。
- **诊断信息**：点名失败主体/路径、违反的规则与修正；删内部执行叙述。

## 工作流

1. 确认 scope、mode、当前分支/PR base、适用的 AGENTS.md；不检查无关分支。
2. 读 [docs/secondary-development.md](../../../docs/secondary-development.md) 与所在代码/文档后再判段落。
3. 检查请求范围（不只最大文件）；用搜索与字数找候选，再语义判定。
4. 分类每个候选：keep/add/trim/restore/restructure/defer；仅在任务授权编辑时应用明确改动，不制造改动去凑删除目标。
5. 先更新 owner 再改派生品；学到新规则后复查同类段落。
6. 跑窄范围相关检查、`git diff --check`，可见字符串配行为测试。
7. 报告检查过的范围、明确改动、刻意保留、延后案例与实际运行的检查。

## 边界判定

仅当至少两个版本都满足「完整命题」规则但权衡不同原则，且本技能未解决该权衡时，才算 borderline。在 automatic 模式下，获授权就应用明确改动，真正 borderline 的报告而不提问；不削弱命题以推进。interactive 模式按治理原则分组同类段落，给出两三个可行版本并推荐其一，说明事实/结构差异；不提供劣质干扰项。用户决定后，把原则与版本蒸馏进参考示例，并将所学规则应用到范围内所有同类段落。
